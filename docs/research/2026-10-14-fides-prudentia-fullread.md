## Fides — mechanism-level distillation

### The two policies

- **Trusted action (P-T).** Enforced on every consequential tool: "This policy permits a tool call to proceed only if the model's decision to call the tool is based exclusively on inputs from trusted sources." Implemented as a static policy label π_f = (𝐓, ⊤) on the *tool*, checked against the dynamic label of the context that generated the call; optionally also per-argument π_x = (𝐓, ⊤). Under P-T enforcement integrity is enforced "in a non-interference flavor": untrusted data cannot even *conditionally* influence whether a consequential action happens.
- **Permitted flow (P-F).** Enforced on egress tools: "This policy permits a tool call that egresses data to proceed only if all recipients are permitted to read the data." π_d = (⊤, R) on the data argument. Crucially, "by default we do not require any specific label on the tool call, i.e. π_f = ⊤. This means that the policy prevents undesired direct flows of data but does not attempt to hide whether data has been sent (which can itself reveal information)." — This "existenzoffen"-artige admission is Fides deliberately declining the RFC's doctrine of Ereignisse as wholes (existence and ordering protected, §6/R.4.2). Not a discovery: the paper says so.

**Policy placement is fixed outside the model.** Three tool classes: consequential (P-T), egress (P-T or P-F, or the combined variant), neither (labels propagate, no gate). A fourth-degree combined policy is what production would use: "It first checks if P-F is satisfied and, if it is not, checks whether P-T is satisfied instead. Specifically, if confidentiality is violated then the tool call is still executed if it is called in a high integrity context, corresponding to robust declassification."

### The formal guarantee — and what it deliberately gives up

Proposition 1: "Algorithm 5 with policies P-T and P-F correctly applied to every tool, guarantees non-interference for the integrity of tool calls and data, and **explicit secrecy** for the confidentiality of data." Explicit secrecy (Schoepe et al. 2016; Volpano 1999) rules out explicit flows only; an adversary watching the tool-call sequence may still infer something through data-dependent control flow. The stated reason is capacity of the user: "preventing implicit information leaks through the sequence or order of tool calls would be overly restrictive (hence explicit secrecy). In this way we achieve a practical trade-off between security and usability."

This is the explicit-secrecy position the scan-level document already flagged. The full read adds the exact mechanism that buys the trade-off: **P-F is checked on arguments only, not on the tool label** — "by checking the tool label for integrity but not for confidentiality, we enforce a strong form of control flow integrity and a weaker form of confidentiality that does not prevent implicit flows." Under the RFC's eigenes Anhang A, this corresponds to giving up the Unabhängige sichtbare Ablaufsteuerung (A.5) assumption; RFC 0003 claims full Nichtinterferenz only under exactly such locality assumptions and does not have to weaken — but a local implementation that cannot prove the A.5 preconditions should fall back to the Fides-tier, and the RFC machinery already supports stating that as a named assumption.

### Variable store with selective hiding

Tool results go through a `Hide` step: hide "recursively checks if any node in the tool result has a security label more restrictive (i.e., not at or below in the security lattice) than the current context label" and, for such nodes, "generates a fresh variable to store that node in memory together with its original label." The conversation continues with the context label unchanged. What is hidden is decided by label arithmetic, not by the model. The AgentDojo evaluation hides on the integrity dimension only: "We do not create variables based on confidentiality labels. Instead, our policies are designed to ensure that there are no confidentiality violations."
### The quarantined, tool-less LLM with constrained decoding

`query_llm` runs an isolated LLM that has no tools, over variable contents, with an output schema enforced "so that the result—returned in a new variable—has a known type." Two-step pattern in data-dependent tasks: extract a bounded decision (bool/enum) with `query_llm`, inspect it, then extract the payload with a second `query_llm` (e.g. `dict(event_details)`) that flows *as a variable* into the sink without the planner ever reading it.

### Labels as security × type lattice

"we define a lattice of types, e.g., bool ⊑ enum["a", "b", "c"] ⊑ string. The order in the lattice is determined by information capacity, where Boolean and enumeration types can carry a bounded amount of information whereas a string output can carry an unbounded amount." Product with the security lattice yields labels (ℓ, ν). Effect: "Low capacity outputs are less useful to deliver prompt injection payloads or exfiltrate information. This allows us to use more flexible policies that consider information capacity, effectively offering declassification or endorsement as escape hatches."

Read with care for the RFC: this is *capacity-bound* downgrading in the type dimension, not a confidentiality Lockerung. The paper itself is conservative about using it: in the meeting-request example, "the above example technically fails to satisfy P-T because the context contains the untrusted contents of #query_llm_0. However, since the untrusted data is a Boolean value rather than an unbounded string, it is unlikely to contain a PIA. An application could use a more permissive policy that allows set_event to be called in this case. However such policies should be used with care as they effectively endorse untrusted values. **In our AgentDojo evaluation we stick to the more restrictive P-T policy.**"

### Labels and provenance: where they may come from

- "In our model, labels originate from data read by tools from the datastore." Enterprise classification (Microsoft Purview), email recipient sets as a readers proxy, Mark-of-the-Web, and "Agent tools can be wrapped to turn such hints into explicit labels. In the absence of labels or hints one can resort to safe defaults."
- "**We ensure that all untrusted tools have trusted wrappers, so that we can assume that all tools label their outputs correctly.**" Untrusted tools return data; trusted wrappers assign labels. The planner never labels anything.
- Per-field granularity is first-class: "a node's metadata label applies to that node and all descendants, allowing a single label for the whole result, per-field labels, or mixed granularity."
- On MCP annotations: "While these annotations are too coarse-grained and might not be reliable, they provide useful **hints** to construct trusted tool wrappers." `readOnlyHint` is not authority (matches RFC R.4.3: „Was der Connector über sich selbst mitteilt … begründet keine Befugnis“).

### Evaluation boundaries (for honest citation)

94 AgentDojo attacks, Tool Knowledge attack, five models except grok-3. With policies: Basic⋆ 9→0 discounting two non-attacks; Fides⋆ 1 (0 after the discount); Variable Passing⋆ 0. Remaining "attacks" are text-to-text manipulations of the final answer (policies run on tool calls only) and one benign-by-policy calendar event. The residual utility cost with policies is real: Fides⋆ trails no-policy Fides by up to 24.5% on o3/o4-mini; token cost 2–3× Basic (Appendix E, "Efficiency"). Failure diagnosis worth importing for Anhang D: after failing to leverage `query_llm`, the planner "falls back to expanding variables directly into the context, tainting it and triggering a policy violation" ("Compensatory leakage").
## Prudentia — mechanism-level distillation

### Framing: autonomy as the payoff of deterministic defenses

New argument, verified at full read: IFC looks expensive when only TCR is measured because "prior work on deterministic defenses … evaluates performance using TCR@0 (calling it TCR) but compares this against undefended baselines that effectively allow unlimited interventions (TCR@∞), thus showing utility loss by contrasting full autonomy requirements with unlimited human oversight." The paper's corrective metric pair:
- **HITL load**: "the total number of HITL interventions on tasks successfully completed."
- **TCR@k**: "the proportion of tasks successfully completed using no more than k HITL interventions per task."

### Endorsement — the mechanism behind the Erstklassifikation comparison

Verbatim mechanism: "The agent can ask the user to endorse untrusted data (i.e. labelled 𝐔) stored in a variable at the moment of expanding it. If the user endorses data, it is relabelled to trusted (𝐓) and the variable is expanded without tainting the context, meaning that future calls to P-T tools can go ahead without requiring HITL approval."

Three properties matter, all verbatim-anchored:
1. **Once per object, not per action.** The motivating example: a benign email labelled 𝐔 containing a TODO list of 10 items, each requiring a P-T call: "Endorsing the email requires a single HITL interaction, after which the agent can autonomously carry out the 10 sub-tasks. In contrast, inspecting the email without endorsement taints the context and would require 10 individual HITL interventions to approve each call."
2. **Agent-initiated, strategically chosen.** Prudentia explicitly does not always endorse: the agent calls `expand_variables(ask_endorsement=True|False)`; Appendix A shows a real trace where the agent declines endorsement because "no privileged tools needed after expanding variables, so can avoid endorsement requests." A dedicated `plan` tool forces a justification whenever expansion is contemplated.
3. **Integrity-only.** The confidentiality-facing dual, declassification, is deliberately absent (below).

### Declassification deliberately absent

"While it seems natural to include declassification as an option alongside endorsement, we decided to forgo this option. This is because whether it is appropriate to declassify private information is often highly dependent on the situation, which is better captured by asking for approval of individual tool calls than by blanket declassification." — Token-level: the paper institutionalizes that Offenlegung ausblieb, exactly the RFC boundary between Freigabe und Herabstufungsbefugnis (R.6.2: „Ein Agent erhält keine wiederverwendbare Herabstufungsbefugnis“).
### Numbers, with their own caveats

- AgentDojo: "With o4-mini, Prudentia reaches 73.2% completion with 19.2 HITL load versus Fides' 75.7% completion with 36.8 HITL load, reducing 1.9× human intervention burden." vs Basic up to 2.9× (o3-mini). TCR@0 on o3-mini: Prudentia 59.1% vs Fides 50.1%.
- WASP: ASR 0 across all four models, HITL load 0. The paper itself defuses the headline: "This result is expected as all the untrusted content is hidden in variables and policy ensures that no consequential tool call can be ever made in an untrusted context." Wasp tasks are all data-independent; attacks were also counted conservatively ("Erring on the side of caution, we consider attacks as successful even if they do not fulfill the attacker's goal but result in the agent being hijacked and diverted from the user task").
- Cost is honest and not negligible: Appendix C shows Prudentia's token overhead well above Fides' (e.g. Workspace, o3-mini: Basic-IFC ≈ 2.97k input tokens, Fides higher, Prudentia an order of magnitude above Basic-IFC) — measured from logged traces, with reasoning-model output-token estimates explicitly not given.

### Where endorsement's human step itself is work-in-progress

"HITL prompts require careful design to prevent attackers from manipulating the information shown to humans. We leave the design of such user interfaces as future work, but anticipate that IFC labels (which cannot be manipulated by attackers) and richer data provenance information could be used to present prompts that assist humans in making informed decisions." — So the endorsement UX (what exactly the human sees and approves) is unvalidated by the paper's evaluation. The RFC's own caveats on manuelle Inhaltsfreigabe (Akrostichon etc., R.6.4) remain necessary.

### Threat model (boundary for Anhang E)

Same as Fides/CaMeL: "user, planner's LLM, and the tool implementations are trusted. The data sources, however, may contain prompt injections." Jailbreaks, direct injection, tool poisoning out of scope; "we focus on security guarantees and do not address other types of model errors such as hallucinations." The famous sentence about what IFC replaces: "IFC can only replace HITL for security purposes but not in general." — Exactly compatible with the GO-Prinzip: GO remains for fachliche/politische decisions; IFC removes only the *security-motivated* subset of constant approvals.
## Against Revision 3's three proposals

### Proposal 1: Remedy plans at B.6 (enumerable catalog of legal continuations)

**Fides sharpens by negative example and by its remedy options.** The paper's planning loop has no recovery semantics: `if ¬policy(action) then abort` (Algorithm 5). The production middleware moves the remedy into the framework, but only as one entry: `approval_on_violation` — "a violation triggers a function-approval request … when the framework can safely bind the approval to the exact invocation. If it can't create that binding, it blocks the call" (Microsoft Learn, retrieved 2026-10-14). So the production FIDES remedy space is {exact-invocation-bound approval, block}. The RFC's B.6 currently stops at `blockers` codes; the APPA ablation (35%→88% task completion) supports the proposal; the full reads add two mechanism-level inputs:

- **The remedy catalog should contain an object-level trust-upgrade entry.** Prudentia's endorsement is measured evidence that one human GO on the object can clear many subsequent blockers (10-for-1 in the TODO example; "reducing the HITL load by up to 2.5× for data-dependent tasks" for the endorsement component). komki's move 1 ("which fact, which GO, which new workspace") already names this; Prudentia supplies the metric and the strategic-choice design (agent proposes, human disposes — GO-Prinzip-kompatibel: `expand_variables(ask_endorsement=…)` is a proposal, the relabel is the human's act).
- **The catalog must distinguish approvable violations from planning failures.** Fides' "compensatory leakage" diagnostic shows a risky remedy shape: after a failing strategy, an agent naturally falls back to an action that violates policy ("compensatory leakage: after failing to leverage query_llm, it falls back to expanding variables directly into the context, tainting it and triggering a policy violation"). A remedy plan that only lists "get a GO for the tainted call" would legitimize that fallback. Prudentia's answer is a non-violating continuation first (replan via `plan`, use `quarantined_llm` again) — the remedy plan at B.6 should enumerate that *before* GO entries, and the Decision output should carry which blocker class (security violation vs. missing fact vs. wrong room) the proposed continuation addresses. This can be tested: Prudentia's HITL load / TCR@k are directly implementable acceptance metrics for D.9 (measure how many GOs a successful task needs given the remedy plans produced).
- One word of caution for citing Fides⋆ zero: the visibility of rejected attempts is a Fides side effect of `abort` at policy check, not an audit guarantee; RFC D-family tests already distinguish protected audit trails from public counters.

**GO-Prinzip compatibility:** both papers pass, with the same pattern — the model proposes continuations, a determinstic gate sets when a human decision is required. Prudentia raises the danger the RFC must design against: confirmation fatigue ("users become desensitized to security prompts and begin approving actions without careful consideration") motivates *fewer, better-bound* GO prompts, not more.
### Proposal 2: Field provenance as a checked duty at B.2/R.4.3

**Fides is the strongest direct support.** Mechanism chain, all quoted above: labels originate at trusted wrappers ("all untrusted tools have trusted wrappers, so that we can assume that all tools label their outputs correctly"); labels are per-node over structured results ("single label for the whole result, per-field labels, or mixed granularity"); MCP annotations are treated as hints only, never authority; derivation is sound over-approximation by join ("responses obtained from the model are tainted by the labels of all the messages … This is sound but may be overly conservative"). The RFC's rule "Sicherheitsangaben aus Agentenargumenten ungeprüft übernehmen" is forbidden (B.2 Kontextauflösung) is the same stance; Fides supplies the production-proven mechanism for the positive side of that rule: *the wrapper labels; the middleware derives; the planner never asserts*.

- **Production detail that sharpens the proposal:** `fides-gateway` puts labels into tool-result `_meta` keyed by RFC 9535 JSONPath queries into the call, evaluates Rego policies per tool call, and drops unknown identifiers fail-closed. For komki, this is a concrete reference pattern for the `ratsinfo_mcp` → `ratsinfo` boundary: the Connector-Fassung of R.4.3 becomes, mechanically, "the wrappings of R.4.3: labels are stamped by gateway middleware on tool result metadata, policies evaluated from that `_meta` before dispatch, unknown values fail closed."
- **The type lattice adds the missing half of "typed metafields."** Proposal 2 says security-relevant typed metafields. Fides shows *why* typing matters, not just decoration: a constrained output of bounded capacity (bool/enum) can be admissible where an unbounded string cannot — "low capacity outputs are less useful to deliver prompt injection payloads or exfiltrate information." Implementation consequence for B.2/B.4: schema-typed facts whereFetcher-provided (not just strings) with an explicit information-capacity notion, so that the Engine can reason about, e.g., a one-bit "public/non-public" marker from a source without treating it as free text. But adopt with the paper's own warning: the capacity-based permissive policy "should be used with care as they effectively endorse untrusted values" — in the RFC's terms such a policy is a documented P_b design decision, not a default.
- **Prudentia's WASP integration is a field-provenance worked example:** "Any user generated content (post or issue description) is marked as untrusted while all other website provided elements (buttons, textarea and others) are marked as trusted. The content in untrusted fields is replaced with variables." No agent argument ever supplies the trust split; it comes from the trusted rendering layer. That is exactly B.2/R.4.3's distinction between an object's own labelled content and agent-selected metadata.
### Proposal 3: Hash-gebundene Commit-Records at B.8/F.5 (ExecutionCommitted binding intent hash, payload hash, Γ snapshot hash)

**Neither paper contains a commit-before-effect protocol; both rely on a *trusted runtime* that the RFC does not assume.** Fides' enforcement sits inside the planning loop between policy check and call execution; Prudentia inherits that runtime. The full read therefore confirms the RFC as sole spec for ExecutionCommitted's three-hash binding — with two sharpenings:

- **Exact-invocation binding is feasible at tool-call granularity in a production framework.** The Agent Framework docs refuse approval reuse when binding cannot be created safely: "when the framework can safely bind the approval to the exact invocation. If it can't create that binding, it blocks the call instead of executing it." That is RFC R.6.3 Reservierung/Verbrauch thinking arriving at middleware level — independently convergent, and citable as evidence that the RFC's requirement is implementable without a blockchain. What remains RFC-only: the Γ snapshot hash (rule-state binding) and append-only journal + verifier; the production system's "Labels and policy decisions are recorded per call" is an audit-trail claim without a hash-commit protocol specification.
- **Threat-model framing belongs in Anhang E as the honest difference.** Both papers trust the user, planner, and tool implementations; the RFC's adversary controls everything inside the Arbeitsraum (R.8.1). Fides' sequential enforcement cannot be retrofitted with the RFC's protocol obligations; that is not a criticism, it is the design space boundary. The RFC's B.8/F.5 gain their justification precisely from dropping the trusted-runtime assumption; Fides/Prudentia then represent the same architecture *with* that assumption granted.

## Corrections and précisions to the scan-level document (2026-10-13)

1. **Fides citation should be v2, not "May 2025" unqualified.** arXiv 2505.23643v2 (3 Sep 2025) is the current version; abstract now includes "and revealing".
2. **Fides production status: verified, and richer than stated.** Microsoft Learn page (2026-10-07) documents FIDES as first-class middleware with secure-by-default unlabeled-output semantics (`UNTRUSTED` + `PUBLIC`), exact-invocation-bound `approval_on_violation`, `quarantined_llm`/`inspect_variable` as automatic security tools, and a separate `fides-gateway` MCP repo. The scan line "In production as the security middleware of the Microsoft Agent Framework, fail-closed by default" is confirmed; the page is opt-in-label-spezifischer than "fail closed" alone implies ("Labels are opt-in per data source … secure-by-default").
3. **Type-lattice claim needs the paper's own conservatism.** The scan's "so one-bit answers from untrusted sources can pass policy" is available-but-not-used: "In our AgentDojo evaluation we stick to the more restrictive P-T policy." Anhang E should not cite Fides as using permissive type-based policies in its evaluation.
4. **Prudentia's WASP zero-ASR needs the structural caveat.** WASP is entirely data-independent tasks; the paper itself calls the 0-ASR/0-HITL result "expected". Cite with the qualifier, not as an empirical tour de force.
5. **Prudentia entertainment-vs-approval: the scan's "the RFC's Erstklassifikation with a usability design" holds, with two prefixes.** Endorsement is (a) strategically chosen by the agent (it may decline to involve the human at all, Appendix A trace), and (b) integrity-only — no confidentiality declassification exists anywhere ("we decided to forgo this option"). Erstklassifikation in the RFC assigns full Bindungen (readers + conditions), a strictly richer act; Prudentia's endorsement only maps to the trust-upgrade part.
6. **Venue status update:** Prudentia's ICLR 2026 is now verified (anchors above). Fides' peer venue remains unverified.
7. New since the scan and worth Anhang E: the Agent Framework's refusal-to-approve-without-exact-invocation-binding ("If it can't create that binding, it blocks the call") is middleware-level corroboration of RFC R.6.3 and the B.8 discipline.
## Adopt / reject / future work against the RFC and komki's five moves

**Adopt.**
- **From Fides:** (a) trusted wrappers as the mechanical form of the fixed Connector-Fassung (R.4.3) at the `ratsinfo_mcp` boundary — stamp labels/labels in `_meta`, policies evaluated from that metadata, unknown identifiers dropped fail-closed (fides-gateway pattern); (b) per-field labels over structured connector results (mixed granularity) for B.2 field provenance; (c) the (security × type) label product with bounded-capacity types for schema-typed facts in B.4, documented as an *evaluated but not exercised* permissive option in the paper; (d) the explicit-secrecy tier as the *named fallback* when A.5 locality assumptions (independent visible scheduling etc.) are not established in a concrete deployment — the RFC's full Nichtinterferenz claim stays, the implementation honesty tier is Fides'.
- **From Prudentia:** (a) endorsement as the measured UX design reference for R.2.5 Erstklassifikation/Freigabe proposals (one object-level GO instead of per-action GOs), with the two provisos below; (b) `plan`-with-justification as the shape of komki-Policy-B.6's remedy plan: a proposed continuation must state why, and which blocker it clears; (c) HITL load and TCR@k as acceptance metrics for D.9 — an implementable version of „Alles zu verweigern reicht nicht"; (d) the paper's argumentation for why a deny-vs-GO distinction must survive at the *security* layer only ("IFC can only replace HITL for security purposes but not in general") — directly quotable for the GO-Prinzip.

**Reject, with reason.**
- **Fides' confidentiality relaxation as an RFC claim.** P-F checked on arguments only, admission "does not attempt to hide whether data has been sent". The RFC's event-whole doctrine (existence, selection, ordering — §6/R.4.2) is stronger and must not be diluted to match Fides' affordance; Fides' property is a Fides property, not an argument.
- **Any blanket endorsement/relabel authority.** Prudentia's endorsement is per-object, at-the-moment, human-decided — compatible with GO-Prinzip. But the RFC additionally forbids „keine wiederverwendbare Herabstufungsbefugnis" (R.6.2) and requires the endorsement/classification decision itself to be registered (Einordnung via autorisiertes Verfahren, R.2.5): the human's relabel is a *governed* administrative act (AdministrationRecorded territory), not a middleware `setLabel()` call. Prudentia records no ledger and no revocation for endorsements — do NOT adopt that absence.

**Future work / notes.**
- Endorsement-UX hardening is explicitly unvalidated in Prudentia ("We leave the design of such user interfaces as future work"): the RFC's manuelle Inhaltsfreigabe warnings (Akrostichon, coding-by-choice — R.6.4) remain the governing caveat; IFC labels + provenance as suggested content for human-facing prompts is a direction the RFC audit work already aligns with (protectors see what bound and what originated).
- Type-capacity-aware policies (Fides) as future work for komki_policy's expression language, if bounded-typed facts ever enter B.4's finite expression space; the paper's own warning about effectively endorsing untrusted values applies verbatim.
- Fides' evaluation-extent observations (AgentDojo lacks IFC ground truth, extended by the authors) are a methodology hint for the D.4/D.9 corpus, not a content commitment.
